# Builder 性能与恢复策略

更新：2026-08-24。

## 已落地的提速

- Melo 句子继续使用长期驻留模型和内容寻址 WAV 缓存；重复文本只合成一次。
- 本机 i7-1360P / 32 GiB 的公开样例基准中，2 个 worker、每个 8 个计算线程为最优：63.65 秒；1 worker 为 78.78 秒，3 worker 反而为 68.16–71.32 秒。因此不把“工作进程越多越快”作为产品选项。
- 0.3.0 将全书待合成句子预先提交到有界 worker 池。第一章准备完成后，FFmpeg 编码当前章时，Melo 同时生成后续章节；输出 Track、Timeline 与 ZIP 顺序保持确定。
- 缓存继续跨便携包升级保留。重复转换、改封面或重新打包时，命中缓存通常比增加进程更有效。

## 用户可选的速度路线

- 质量优先：Melo“加速（推荐）”，满足 CPU/内存门槛时使用 2 worker。
- 内存优先：Melo 1 worker，峰值更低但耗时更长。
- 速度优先：Windows SAPI，通常启动更快、占用更低，但音色和自然度由系统已安装声音决定。

## 不建议盲目采用

- 增加到 3 个或更多 Melo worker：本机已实测更慢，并显著增加约 5 GiB/模型级别的内存压力。
- 同时启动多个 FFmpeg 编码：AAC 编码不是当前主瓶颈，额外并发会与 CPU TTS 争用。
- 在当前主机上切换 CUDA：没有可用 NVIDIA CUDA 设备，当前 PyTorch 为 CPU 路线。

## 后续可验证

- CosyVoice 多音色 Provider：先测 CPU 实时率、峰值内存、长文本稳定性和离线模型许可；它解决音色丰富度，不预设一定比 Melo 更快。
- 轻量 ONNX/Piper 路线可能显著提高 CPU 实时率，但必须先完成中文声音质量和 GPL 分发影响评审。
- 若未来更换带 NVIDIA GPU 的宿主机，单独建立同文本、同音色、冷/热缓存的端到端基准，再决定是否提供 GPU 后端。

## 看门狗边界

Melo 单句与 FFmpeg 单 Track 最多等待 12 分钟，超时只重启该最小步骤并自动重试一次；最终包失败只重建 staging。第二次失败停止并保留有效 WAV 缓存。GUI 在连续 10 分钟没有真实进度时显示观察提示，不把提示本身计作进度。
