# AI Agent 维护指南

本文是任何自动化开发 Agent 进入本仓库后的公开维护入口。它只包含可公开的仓库规则；本机路径、设备标识、任务 ID、私有文档页面和凭据位置由维护者的本地 `AGENTS.md` 与本地交接包管理。

## 1. 开始工作前

1. 从仓库根目录开始，先读取根 `README.md`、受影响产品的 `README.md`，以及本文件链接的审计和发布标准。
2. 一次任务只修改用户明确放入范围的产品。共享规则、CI、签名脚本或跨产品协议变更应由路线协调任务统一管理。
3. 开始前检查 `git status`、当前分支和基线提交；不得覆盖其他任务或用户留下的修改。
4. 需要真实手表或手机时，先说明所需设备和原因，并等待用户确认连接。没有确认不得扫描、查询、安装或操作设备。
5. 任何秘密、签名材料、私人页面 ID、设备序列号、本机绝对路径、用户内容和原始敏感日志都不得进入 Git。

## 2. 仓库与产品边界

本仓库是所有 Watch App 产品唯一的 Git 仓库；产品目录不得再初始化嵌套仓库。

| 产品 | 代码范围 | 用户可见组成 |
| --- | --- | --- |
| 能力探针 | `X3AccessibilityProbe/` | 内部硬件与系统能力探针 |
| 记账 | `X3VoiceLedger/` | 手表 App、手机伴侣、BLE 同步与数据工具 |
| 笔记 | `X3WolaiNotes/` | 手表端 Wolai 笔记与个人 Token 配置 |
| 听读 | `X3OfflineReader/` | 手表端离线播放器与 Windows 听读工坊 |
| 日程 | `X3Schedule/` | 手机端编辑、手表端查看/反馈及双端同步 |

跨产品公共内容位于：

- `gradle/`：共享质量与签名配置；
- `scripts/`：仓库级审计、签名、网络和发布门禁；
- `config/`：机器可读的审计与发布标准；
- `docs/audit/`：代码审计 profile；
- `docs/release/`：WARS 与发布验收边界；
- `design/icon-system/`：应用图标设计规范与维护源。

## 3. 文档归属

应提交到 Git 的内容：源码、构建配置、产品 README、协议/开放格式、Schema、验证器、可复现的合成 fixture、维护中的设计源和公共维护规范。

不得提交到 Git 的内容：任务协调信息、本机路径、固定设备标识、私有文档页面、签名材料、凭据、用户数据、构建输出、依赖目录、缓存、临时下载、验收截图和原始设备日志。

功能、架构、版本、数据格式、安全边界或已知限制发生实质变化时，同时更新：

1. 受影响产品的 README/规格；
2. 对应测试和可复现 fixture；
3. 发布或迁移说明；
4. 维护者指定的在线项目索引与本地过程文档。

## 4. 编辑规范

### Java / Android

- 以 Google Java Style 为基线，并遵守现有项目结构。
- 保持包名、应用 ID、数据目录、数据库/备份格式、BLE 协议和签名身份兼容。
- 审查生命周期、资源释放、并发、异常处理、权限、导出组件、Intent 输入和数据迁移。
- OPPO Watch X3 是定制 Android 环境，不得假设标准 Wear OS API 或行为。
- 圆屏关键文本和控件避开四角；第一方内页保持右滑返回。
- 使用公共 Android API；不得 root、解锁、修改系统分区或绕过安全机制。

### Gradle / Groovy

- 固定重要工具和插件版本，配置应确定、可读且失败关闭。
- 不复制或绕过共享质量、Debug 签名和 Release 签名规则。
- 禁止在脚本中硬编码密钥路径、别名、口令、Token 或私人配置。

### PowerShell

- 验证参数、使用 `-LiteralPath` 处理文件、正确传播错误并保证幂等。
- 破坏性操作必须精确限定目标，并先验证路径、跟踪状态和重解析点。
- 日志不得输出 Token、密码、密钥内容或原始敏感数据。

### Vue / TypeScript

- 运行 ESLint、类型检查、测试和生产构建。
- 保持组件边界、响应式状态、异步错误和 IPC 输入验证清晰。
- 生成的 JavaScript、声明文件、`node_modules` 和构建目录不进入版本控制。

### Rust / Tauri

- 运行 `cargo fmt --check`、`cargo clippy --all-targets --all-features -- -D warnings` 和测试。
- 审查 Tauri command 暴露、路径/URL、序列化、panic、权限和前后端信任边界。
- `unsafe` 必须有不可替代的理由、局部范围和验证证据。

## 5. 签名与凭据原则

- 所有 Android Debug 应用必须使用维护环境提供的同一开发证书。缺失或摘要不符时停止，不得生成替代证书。
- Release 使用仓库外、独立备份的正式证书；任何 Release 密钥或口令均不得进入仓库。
- 覆盖升级优先使用兼容签名的安装方式；不得用卸载重装规避签名问题，除非用户明确接受数据和权限丢失。
- Windows 正式安装器必须通过 Authenticode；没有证书时只允许明确标记的未签名个人预览便携包。
- Wolai 笔记只保存用户自行导入的个人 Token，界面不得回显完整 Token；Token 只能删除并重新导入，不能明文编辑。
- GitHub、在线文档和 MCP 的登录由本机凭据系统或环境变量提供；Agent 只验证“已配置”，不得读取、复制或打印秘密值。

## 6. 验证矩阵

修改后至少运行受影响范围的检查；跨产品或发布变更还要运行仓库级 CI 等价门禁。

| 变更类型 | 最低验证 |
| --- | --- |
| Android | Checkstyle、单元测试、Android Lint、Debug 构建；安装前验证 Debug 证书 |
| 数据/同步/迁移 | 合成数据回归、旧版本迁移、重复/冲突/离线恢复、备份恢复 |
| 听读工坊 Java | Gradle 测试与打包相关测试 |
| Vue/TypeScript | ESLint、类型检查、测试、生产构建、`npm audit --audit-level=high` |
| Rust/Tauri | fmt、clippy `-D warnings`、测试 |
| Python | 相关测试与语法编译检查 |
| PowerShell | 解析检查、可用时运行 PSScriptAnalyzer、正负例 fixture |
| 发布/共享配置 | 审计 profile、WARS、网络安全、公开源码边界、签名验证和 GitHub CI |

权威入口：

- `docs/audit/WATCH_APP_AUDIT_PROFILE.md`
- `docs/release/WARS_1_0.md`
- `docs/release/PRODUCTION_ACCEPTANCE_CHECKLIST.md`
- `docs/release/PUBLIC_SOURCE_STATUS.md`
- `.github/workflows/android-quality.yml`

自动化通过不等于实机通过；模拟器、合成验证、实机前台、实机后台和长期耐久证据必须准确区分。

## 7. Git 与发布流程

1. 从最新 `main` 建立短期 `codex/` 分支。
2. 只暂存任务范围文件，检查 diff、秘密、生成物和外部文档边界。
3. 本地门禁通过后推送并建立 PR。
4. PR 的 `verify` 必须通过；合并后再次确认 `main` CI。
5. `main` 禁止强推和删除。任何历史重写必须由维护者单独批准。
6. 源码公开、个人预览二进制和正式生产发布是三个独立结论，不得互相替代。
7. 发布说明必须记录源码提交、版本、轨道、签名状态、SHA-256、已知限制和验证范围。

仓库当前没有统一开源许可证。公开可见不代表获得复制、修改或再分发许可，也不代表可以接受外部代码贡献。

## 8. 任务结构与职责

维护工作采用“路线与协调任务 + 产品开发任务”的层级：

- 路线与协调任务：拥有跨产品硬件结论、公共标准、审计顺序、共享配置、主分支、公开发布和新产品建档。
- 产品开发任务：只拥有自己的产品目录、产品文档、测试和发布候选；不得自行修改全局审计/发布标准。
- 能力探针默认由路线任务管理；探针只证明设备能力，不承载产品业务。

跨任务交接必须包含：精确目录范围、基线提交/分支、当前 dirty 状态、标准版本、签名规则、验证要求、文档入口、已知限制、设备连接状态和准确下一步。任务 ID、私有在线文档和本机路径由本地交接包提供，不写入公开仓库。

## 9. 创建新产品

1. 在仓库根建立一个直接命名的产品目录，不创建嵌套 Git 仓库。
2. 先建立产品文档页和专用开发任务，明确包名、路径、架构、范围、限制、状态、测试、决策与下一步。
3. 新的 `com.android.application` 模块接入共享 Debug 签名并扩展证书验证脚本。
4. 接入 Checkstyle、Lint、单元测试、CI、审计 profile、WARS 和公开源码边界。
5. 若涉及图标，遵循 `design/icon-system/SPEC.md` 和平台图标规范。
6. 设备验证只证明本次实际覆盖的型号、构建和场景，不把短时前台结果泛化为长期后台可靠性。

## 10. 停止和恢复

长任务在每个实质里程碑后保存可恢复检查点。检查点至少包含：目标/范围、标准版本、分支和基线、dirty 文件、完成修改、测试结果、开放风险、下一步、文档状态和设备状态。

若执行环境采用额度门禁，应在工具密集阶段前和里程碑后检查额度；到达维护者规定的停止阈值时不得开始新修改，应先保存检查点再停止。恢复后先核对检查点、Git 状态和相关文件，避免重复工作。

## 11. 持续交接门禁

任何实质 Git/GitHub 更新或在线项目文档更新，都必须在同一任务序列内同步维护者指定的本地交接包。应假设当前 Agent 可能在任意里程碑后永久退出，因此交接资料必须持续反映最新代码基线、文档状态、验证结果、开放风险、责任归属和准确下一步，而不是只在正式交接时临时整理。

变更完成前至少核对：

1. 公开代码、README/规格和 GitHub 状态是否一致；
2. 对应在线产品页是否反映最新架构、版本、测试、安全、限制和下一步；
3. 本地交接基线、机器可读清单、任务拓扑及接管指令是否需要更新；
4. 三处记录是否均未包含 Token、密码、密钥内容、私有页面 ID、任务 ID、设备序列号或不应公开的本机信息。

若在线文档只是私人决策或过程记录，不应为追求形式一致而复制到公开 Git；应在本地交接包中记录可恢复结论，并只把公开、代码相关的信息写入仓库。
